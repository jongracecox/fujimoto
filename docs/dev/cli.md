# Entry point and CLI commands

`cli.py:main()` is the package entry point (`pyproject.toml` `[project.scripts]`). It parses CLI args:
- `--version`/`-V` prints `fujimoto {version}` and exits
- `--create-config` writes a commented `.fujimoto.yaml` template to the repo root (via `project_config.write_config_template`) and exits; errors (already exists, not a git repo) print to stderr and exit 1.
- `--debug` / `--debug-redacted` turn on diagnostic logging (see `debug.py`) before anything else runs, via `_start_debug_log(redact=...)`; `_finish_debug_log()` closes the log on every exit path (normal quit, prerequisite failure, fatal error, KeyboardInterrupt, and the `pane` subcommand). Both flags work alongside `pane`.
- `fujimoto new <title> [--base B | --current] [-- claude args…]` creates a worktree via `_new_worktree_target` (the CLI twin of the TUI's create flow: no flag → fetch and start from `origin/<default>`, offline → local default; an existing worktree for the title is connected to, not duplicated) and hands its `LaunchTarget` to the launch loop as `initial_target`, so the **first** iteration skips `SessionApp` and every later one is the normal TUI — detaching lands on the home screen and `Ctrl-A f/s/x` hand-offs work unchanged. Arguments after `--` become `LaunchTarget.claude_args` and are saved like a dialog choice. `_split_claude_args` splits `sys.argv` at the first `--` by hand before `parse_args`, because argparse's `--` handling with `nargs=REMAINDER` has changed between Python versions; `--` with any other command is a usage error.
  `_prepare_new_session` adds the rest: a session that isn't already running gets a fresh `uuid4` as `LaunchTarget.session_id` (→ `claude --session-id`, and recorded on the `SessionRecord` by `mark_open`, so the id is known before any transcript exists) and `--prompt` as `LaunchTarget.prompt` (claude's positional first message). Neither is saved or replayed, which is why the prompt is not a launch option. `--prompt` against an already-running session exits 1. `--detach` calls `_start_launch(target, attach=False)` — the launch-loop body, factored out so both paths share it — then prints `_new_session_result` as JSON and exits without the TUI. In that mode stdout is reserved for the JSON: `_stdout_to_stderr` redirects **fd 1** (not `sys.stdout`, which a child process never sees) around the launch so `.fujimoto.yaml` init output goes to stderr, `_apply_worktree_config(interactive=False)` skips the keypress pause, `set_terminal_title` is skipped, and the `--debug` "log written to" notices print to stderr (always, now).
  `--parent NAME` records the starting session's peer address in the worktree's meta (on create *and* on connect) via `write_parent_session`. `_build_system_prompt` appends `_parent_system_prompt(name)` for a worktree that has one, and `_start_launch` passes that sentence alone as the system prompt on a **resume** — the appended system prompt does not carry over into a new claude process, so without it a resumed child would lose its parent. `_new_session_result` reports it as `parent_session`. A child's own address is set with claude's `--name` after `--`, which is saved as a launch option and so is stable across relaunches; Claude Code's derived names (`<cwd basename>-<2 hex>`) are not predictable, and a session id does not work as a `SendMessage` address.
- `fujimoto list [SESSION...] [--project NAME|PATH | --all-projects] [-n N] [--running] [--waiting] [--state LIST] [--json [--fields LIST]]`, `fujimoto search QUERY [--project NAME|PATH | --all-projects] [-e] [-s] [--raw] [-n N] [--sort recent|relevance] [--include-self] [--json]` and `fujimoto log SESSION [--summary | --grep P [-e] [-s] [-C N]] [--head N | --tail N] [--roles LIST] [--after CURSOR] [--reply-to ID] [--wait SECS] [--json [--fields LIST]]` are the read-only query commands, dispatched to `_run_list_command` / `_run_search_command` / `_run_log_command` **before** `_check_prerequisites` — they must work without tmux, and never open the TUI. All logic lives in `session_query.py`; `cli.py` only parses arguments, maps `QueryError` to exit 1 and prints. Text is the default output (for people *and* agents), `--json` the structured form. No match is exit 0. `list` builds `Scope(all_projects=True)` itself when sessions are named (scope flags are ignored, never resolved), parses `--state` in argparse (`_session_states`, exit 2) and `--fields` with `session_query.parse_fields` (exit 1, like every `QueryError`); `--fields` without `--json` is an error. `log --fields` works the same way, validated against `LOG_FIELDS`. `list` and `search` pass `outside_repo_all=True` to `resolve_scope`, so with no scope flag outside a repo they cover every project; `chat` does not, since it needs one project.
- `fujimoto resume SESSION [--fork] [--detach [--wait SECS]] [--prompt T] [--parent NAME] [-- claude args…]` is `new`'s twin for an existing conversation, and shares its plumbing: `_prepare_resume` returns a `LaunchTarget` for the launch loop's `initial_target`, or with `--detach` calls `_start_launch(attach=False)` under `_stdout_to_stderr` and prints `_resume_result` JSON. Rules, in order: an unknown id or unreadable log → exit 1; a missing `cwd` → exit 1 naming the branch (no recreation); already running (by `ActivityIndex`) and no `--fork` → connect (attached) or report (detached), **never a second process on one transcript**, and `--prompt` is an error since only a new process could take it; otherwise `_resume_cli_target` names the tmux session: a stopped session whose record still holds this conversation id (`_record_owning`; a chat, typically) comes back under its own name and type, and only then as the TUI's `_resume_target` does (the worktree's own name if free, else `session-N`; `adhoc-N` outside a repo). A fork never reuses a record. `LaunchTarget` gained three `resume`-only fields: `extra_args` (appended after the launch options and **never saved**, which is how the automatic `--name <worktree>-<id8>` / `<worktree>-fork-<hex4>` avoids overwriting a session's chosen options; skipped when the options already set `--name`), `fork_in_place` (`--resume <id> --fork-session` in the same directory, recorded with no id until `wait_for_registration` finds the new one in Claude Code's registry and `mark_open` stores it) and `parent_session` (the `--parent` prompt for sessions with no `meta.json`). claude does not document `--session-id` with `--fork-session`, which is why a fork's id comes from the registry rather than being chosen up front.
- `fujimoto stop SESSION [--json]` (`_run_stop_command`) resolves a tmux name directly, or a Claude session id via `session_query.tmux_for_session` (registry/tmux, refusing one running outside tmux), then `kill_session` + `mark_stopped`, the same as `Ctrl-A s`. It runs before the prerequisite check.
- `fujimoto config [list|get KEY|set KEY VALUE|unset KEY] [--global|--project] [--json]` (`_run_config_command`, logic in `config_command.py`) runs before the prerequisite check. Bare `config` is `list`. `set`/`unset` *require* a scope flag (argparse mutually-exclusive group, `required=True`); `get` without one prints the effective value and exits 1 when unset, like `git config`. `config set` is the third command allowed a `--` remainder (after `new`/`resume`): `config set claude_args --project -- --verbose` passes a value argparse would otherwise read as a flag, joined back with `shlex.join`. Giving the value both before and after `--` is an error.
- **Every launch's system prompt ends with `FUJIMOTO_CLI_PROMPT`** (`_with_cli_prompt` in `_start_launch`, covering new, fork and resume — a resume otherwise gets only the parent link, since an appended system prompt does not survive into a new process). It points the session at `fujimoto agent-instructions` and names `fujimoto config`; without it, a session asked to "show the fujimoto config" read the YAML files instead. Keep it one sentence: it is paid on every launch.
- `fujimoto update [check|dismiss [VERSION]] [--json]` (`_run_update_command`, logic in `version_check.py`) runs before the prerequisite check. Bare `update` is `check`, which asks PyPI *now* (`refresh_latest`, ignoring the daily interval, falling back to the cache offline) and prints the install method and upgrade command from `detect_install`. `dismiss` writes `agent_dismissed_version` (default: the cached latest; exit 1 when none is known, or when the write fails, since an agent should hear the dismissal did not stick).
- **New sessions are offered a newer fujimoto.** In `_start_launch`'s new-session branch only (not resume or fork: a resume would ask again on every reattach), `_update_notice` appends `agent_update_notice` when `pending_agent_update` finds a cached latest release newer than the running version and not agent-dismissed. It reads the cache only, never PyPI, so a launch never waits on the network; the TUI's daily check keeps the cache fresh. The sentence names the upgrade command for this install and offers three answers: yes (upgrade), not now (do nothing, so a later session asks again) and don't ask again (`fujimoto update dismiss <version>`). A plain "not now" deliberately doesn't dismiss: that would make the first refusal permanent for the version.
- `fujimoto restart [--all] [--json]` (`_run_restart_command`) runs before the prerequisite check. Without `--all` it targets `current_session()` (from `$TMUX_PANE`) and exits 1 with an explanation outside tmux. For each session, `tmux.loop_client` must find a client whose parent is the loop pid in `@fujimoto_loop_pid`; otherwise the session is skipped (single target: exit 1), because detaching a plain `tmux attach` would strand the user at a shell. Found → `request_restart` sets `@fujimoto_pending_action restart` and detaches *that* client only. The hidden `--session NAME` is the `Ctrl-A r` binding's entry point (`run-shell` has no pane): it prints nothing and reports a failure with `display_message`, since `run-shell` output would cover the pane.
- **Restart re-executes the loop in place.** When `take_pending_action` returns `PENDING_RESTART`, `_restart_fujimoto` calls `os.execv` on `sys.argv[0]` (else `fujimoto` from `PATH`) with the original `--debug`/`--debug-redacted` flags and the hidden `--attach NAME`. `exec` keeps the pid and the tty, so the new code runs in the same terminal pane; it returns only on failure, and the old loop carries on to the home screen. `--attach` builds the target from the session's record (`_reattach_target`; no record or no session → home screen) and `_reattach` only sets the title and calls `attach_session` — no worktree config, record update or launch, since the session is already running.
- `fujimoto chat [TITLE] [--in WORKTREE | --in-scratch] [--project NAME|PATH] [--prompt T] [--parent NAME] [--detach] [-- claude args…]` (`_prepare_chat`) starts a chat session (see [Session types](sessions.md#session-types)) without creating a worktree. The project comes from `session_query.resolve_scope` (cwd, or `--project` path/name), so it shares `search`'s rules. Location: the project root by default; `--in` via `_pick_worktree` (exact name, else the one name containing the text; none/several → exit 1 listing them); `--in-scratch` (hidden alias `--in-temp`, its first name) the project's scratch directory, reporting `needs_trust` (JSON) plus a stderr hint when `claude.trust.is_trusted` says Claude Code has not trusted it yet. The name is `next_session_name(..., fallback="chat")` against every tmux session, every record and every worktree name. A fresh `--session-id`, `--prompt`, and — unless the launch options already set one (`_peer_name_in`) — an unsaved `--name <project>-<chat name>` in `extra_args`, so the JSON's `peer_name` is a real address before the process registers. `--parent` goes onto the *record* (`mark_open(parent_session=…)`), since a chat has no `meta.json`. `chat --detach` is dispatched before `_check_prerequisites`, so with `--project` it works from outside any repo; attached, it is the launch loop's `initial_target` like `new`.
- `fujimoto send SESSION TEXT [--ttl] [--key] [--wait] [--json]` (`_run_send_command`) messages one listening session through the same machinery (see `broadcast.py`, "Single-session target").
- `fujimoto broadcast <send|status|verify|show|enable|disable|add-signer|remove-signer|set-role|set-key>` (`_run_broadcast_command`) runs before the prerequisite check, like the query commands, mapping `BroadcastError`/`OSError` to exit 1. Logic and text output live in `broadcast.py`; the config subcommands go through `_broadcast_config_change`, which reads `broadcast.load_config(strict=True)` and writes `broadcast.save_config` (the global config's `broadcast` key, via `update_global_key`). `send` with no scope flag targets the cwd's project (`get_project_name`), outside a repo it is an error. `_start_launch` calls `broadcast.launch_args(project, working_dir, claude_args)` **after** `_launch_claude_args`, so the hooks are never saved as a session's launch options.
- `fujimoto mcp [--key KEY]` / `fujimoto mcp setup [--key KEY] [--name N] [--json | --config-only]` (`_run_mcp_command`) run before the prerequisite check. Both import their module lazily (`mcp_server`, `mcp_setup`), so the main CLI never imports the `mcp` extra. `setup` exits 1 when a check fails. See [`mcp_server.md`](modules/mcp_server.md).
- `fujimoto agent-instructions` prints `templates/agent_instructions.md` (`session_query.agent_instructions()`, via `importlib.resources`) — a slim guide for agents to the session commands and when to use them. **Keep it in step with the CLI**: `TestAgentInstructions.test_every_example_parses` runs every `fujimoto …` line in it through `_build_parser()` (the parser, extracted from `main()` for exactly this), and `test_stays_generic` checks the only ticket key in this shipped file is the `ABC-123` placeholder. Examples must stay synthetic (`ABC-123`, `8f0e2c1a`).
- `fujimoto pane <vscode|terminal> --session <name>` dispatches to `_run_pane_command`, used by the in-session tmux key table (`Ctrl-A v` / `Ctrl-A w`). Resolves the session's working directory via `tmux display-message -p '#{session_path}'` and calls the existing `open_vscode` / `open_terminal` helpers; errors are surfaced via `tmux display-message` so they appear in the session's status bar.

Otherwise it:
1. Runs the Textual `SessionApp` in a loop
2. After the TUI exits, calls `launch_claude_in_tmux()` if the user selected a session
3. When the tmux session is detached, the loop restarts and the TUI reappears
4. The loop exits when the user quits the TUI (q/escape/ctrl+c) without selecting a session
